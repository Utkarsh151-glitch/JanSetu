## User flow

- **Applications** in bottom navigation and **My Applications** in Settings open the local profile. Lists use lazy rendering, status filtering and upcoming deadline/submission date/latest update sorting. Past or missing deadlines sort after upcoming deadlines.
- **Add manually** supports services outside the pilot. No official URL, eligibility, jurisdiction or verified association is inferred for a manual entry.
- Published/verified online services with a confirmed official application URL offer **Add to My Applications**. The editor captures service identity/name, department, actual jurisdiction, catalog version, information/application/source links and source-check date. Title and department labels are editable; captured provenance stays separate. Information-only and assisted entries have neither active Apply nor service-prefill actions.
- New records start **Planning to apply**, with no submission date. Opening the official portal never creates a submission or changes status.
- Users can record all eight requested statuses, optional submission/reference/deadline/notes/reminder and a dated progress note. Status changes and progress notes append events; changing other fields preserves earlier history. Dates use explicit YYYY-MM-DD input and validation; missing optional dates are valid. Invalid dates, future submission/progress dates and a deadline earlier than submission produce explanations without saving. Historic deadlines may be saved with reminders off.
- Details show **Your recorded status**, captured official links, source snapshot date, history, masked reference with deliberate reveal, creation/update times and reminder state. Missing current catalog associations retain the saved snapshot and disclose the mismatch. Neither status nor search ranking is an eligibility/government-status decision.
- Editing uses a revision check to prevent a stale draft overwriting a newer record. Saved records survive rotation/process restart; unsaved form fields use Compose saved-instance state for restoration. Save is explicit. One/all deletion requires confirmation and cancels reminders. Catalogs, favorites and preferences are separate.

## Storage, schema and recovery

`tracker/ApplicationRepository` is a blocking interface; Compose invokes it on `Dispatchers.IO`. `SqliteApplicationRepository` uses platform SQLiteOpenHelper without adding a database/compiler dependency. Tables are `applications`, `progress_events` and `reminder_deliveries`. Foreign keys cascade a record's events/delivery marker only. Record/history writes are one transaction; queries and mutations serialize across repository instances. All user-content payloads use AES-256-GCM through Android Keystore with fresh provider-generated IVs and authenticated row identities. The key is non-exportable through the app. UUIDs, relationships and reminder fingerprints remain structural metadata, not private notes or reference values.

Database path: `context.noBackupFilesDir/tracker/applications.db`. Schema v2 adds only duplicate-delivery bookkeeping to the defined v1 application/history layout. The upgrade is additive; unsupported downgrades fail instead of dropping tables. There was no released tracker database before this phase. Migrations/reopen use the same key.

An unreadable record is counted, retained and withheld from the readable list; its failed edit cannot overwrite its bytes. Other readable records remain usable. Database-level failures show a storage error instead of an empty profile. A custom SQLite corruption handler prevents the platform's default destructive recovery. Retry does not reset data. Unreadable record placeholders offer confirmed removal of that record alone. **Remove all tracker data** is the deliberate whole-store recovery option when the user accepts losing it. `secure_delete` is enabled; active records/history are removed on deletion. Filesystem forensic erasure is not promised.

No cloud login/database, analytics, uploads, private-data logging or automatic export is present. Cloud backup/device transfer are explicitly excluded for app storage, in addition to `allowBackup=false` and the no-backup database location. Loss of device/key, uninstall or app-data clearing can lose records permanently. Encryption does not hide data displayed on an unlocked/compromised device. Reference fields are masked; private notes are shown inside the app. OS-managed form saved state can retain unsaved draft fields for restoration and is not cloud synchronization.

## Local reminder policy

- Explicit opt-in per application; deadline required. Options: deadline day or 1/3/7 days before, around **09:00 device local time**. Past reminder times are rejected in the editor; closed applications disable reminders. Changing deadline/offset or disabling/removing the record replaces/cancels its schedule.
- Platform `AlarmManager.setAndAllowWhileIdle` with RTC wakeup is inexact. No exact-alarm permission, network constraint, server or periodic polling is used. Android may delay/prevent reminders due to power restrictions, notification settings or force-stop. Scheduling is not delivery confirmation.
- Android 13+ POST_NOTIFICATIONS is requested only when the user chooses Enable notifications. App/channel settings are checked; a settings action remains available after denial. Denial preserves the record/reminder preference and explains that no alarm is scheduled. After enabling notifications, app resume reconciles future reminders. Older Android uses app/channel availability checks.
- PendingIntent identity uses one opaque record UUID, so rescheduling replaces the previous alarm. Alarm input contains UUID/fingerprint only. A private preferences registry retains opaque alarm IDs for cancellation, including deliberate recovery from unreadable database contents; it is excluded from backup.
- Boot, timezone, clock and package-replacement broadcasts, plus app resume, reconcile future records in the current timezone. Calendar-day arithmetic handles offset/DST transitions, and the current timezone is read again within an existing process rather than captured at startup. A reminder already past its scheduled time is not newly scheduled on reconciliation; review deadlines in the app if a device was off or force-stopped.
- Delivery re-reads the saved record and checks deadline preference, time window, notifications and a persistent duplicate marker. Deleted/changed/closed/expired records do not post. A stable notification tag prevents duplicate visible cards. A crash between posting and committing the marker can retry the same tagged notification; notification posting and SQLite cannot be a single atomic transaction.
- Notification title/body are generic, with no application title, reference, note, service name or recorded status. Visibility is private; tapping opens the record. **Posted** means the platform notification call succeeded, not that the person received or read it.

## Future profile boundary and remaining scope

[APPLICATION_TRACKING_BOUNDARY.md](APPLICATION_TRACKING_BOUNDARY.md) separates this local repository from any future authenticated sync/provider model. There is no live government-status provider. Full translation of tracker screens, multi-device testing, full spoken accessibility assessment, physical-device battery/reboot/OEM scheduling behavior and production privacy/store review remain additional work. This functional phase does not redesign Home/Search or change third-party website UI permissions.

Platform basis: [SQLiteOpenHelper](https://developer.android.com/reference/android/database/sqlite/SQLiteOpenHelper), [Keystore cryptography guidance](https://developer.android.com/privacy-and-security/cryptography), [backup exclusions](https://developer.android.com/identity/data/autobackup), [inexact alarms](https://developer.android.com/develop/background-work/services/alarms), [notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).
